# CBU Autonomous Robot workspace — Claude Code context

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
CBU Autonomous Robot: an autonomous robot that escorts students to classrooms in the CBU Engineering building using SLAM navigation. Capstone team: Lancer Automation Systems. The real robot runs on a Jetson Orin Nano (needs JetPack 7.2+ for Ubuntu 24.04 / native Jazzy; JetPack 6 is 22.04 / Humble) with a 2D LiDAR only (no depth or RGB camera). This workspace is the simulation and software side; a DRL hallway-navigation policy will be trained here in simulation (CSCI 4220 project).

## Project Plan (CSCI 4220 proposal — Morente, Davis, Leon Duran)
- **Goal:** RL policy for local navigation in a dynamic, pedestrian-occupied corridor: reach a goal from LiDAR ranges + goal position only, without hitting obstacles or people. Success = the final model beats our initial baseline on the metrics (no absolute target). Training difficulty ramps up: fixed world → randomized spawn/heading/goal/static obstacles → moving pedestrians; final test in an *unseen* environment. Named risks: reward hacking (e.g. speed over safety; handle with reward shaping and safety penalties that don't over-constrain), training compute, sim-to-real transfer.
- **Hierarchical agent** (after de Heuvel et al. 2023, arXiv 2303.01443): a high-level *subgoal agent* picks intermediate subgoals toward the goal around obstacles; a low-level *motion agent* turns LiDAR + current subgoal into linear/angular velocity. Choi et al. (PMC8493784) motivates stacking previous-timestep observations so the policy can react to moving obstacles. The current flat `cash_rl` PPO policy (static world, no pedestrians) is the natural single-layer baseline to compare against.
- **Metrics:** goal completion rate, collision rate, path length, navigation time — `evaluate` already reports all four (success, collisions, `path` ratio, `time_s`).
- **10-week schedule:**

  | Wk | Focus |
  |---|---|
  | 1 | PyTorch ramp-up |
  | 2 | Sim world, robot, 2D LiDAR |
  | 3 | Verify sim: LiDAR accuracy, controls, collision/goal detection, metrics logging |
  | 4 | High-level (subgoal) agent: obs, actions, reward |
  | 5 | Low-level (motion) agent: velocity commands from LiDAR + subgoal |
  | 6 | Integrate the two agents; test in a simple env |
  | 7 | Midterm checkpoint; randomize spawn, goal, obstacle positions |
  | 8 | Dynamic obstacles (pedestrians): predictable paths first, then random speeds/positions |
  | 9 | Final testing on unseen environments |
  | 10 | Analyze results vs. baseline; final presentation, sim-to-real limitations |

  The proposal mentions PyBullet, but the project uses Gazebo + `HallwayRaycastEnv` instead. Weeks 2–3 and the static randomization in week 7 are effectively done (see milestone 3). Hierarchy and pedestrians are not built yet.

## Package: src/cash_rl (ament_python)
- `cash_rl/spec.py`: single source of truth (no ROS imports) for the goal-reaching task, mirroring the URDF (keep in sync). Both envs import it, so a policy trained in one runs in the other unchanged. Observation (113): the last 3 scans (`N_SCAN_STACK`, one per 0.1 s step, newest first; reset fills all 3 with the first scan) of 36 of the 2160 beams clipped to 10 m (the STL-27L's range on dark surfaces) / 10 m, goal distance / 30 m + cos/sin of goal bearing in the robot frame, previous action. Models trained before stacking (41-dim obs) still load: `train.load_model` wraps them to see only the newest scan (`spec.single_scan_observation`). Action: [-1,1]² → 0.5 m/s forward / 0.15 m/s reverse (capped so policies turn around instead of backing up), 1.0 rad/s. Collision: any return inside the 0.50×0.49 m footprint (width = wheels' outer faces) inflated by 0.05 m. Reward per step: 10 × decrease in *geodesic* goal distance − 0.01, +10 on reaching (within 0.3 m), −20 on collision (−40 if it hit a pedestrian), and with pedestrians up to −0.3 per pedestrian per step inside a 0.8 m gap, ramping linearly to the full amount at contact (`PEDESTRIAN_*` constants, `pedestrian_proximity_penalty`; waived along with the time penalty while the robot waits — forward speed < 0.05 m/s with a pedestrian inside 0.8 m, `waiting_for_pedestrian` — though being walked into still costs −40; plus a *lane* penalty, up to −0.3 per pedestrian per step while the footprint is in a pedestrian's walking lane and it would reach the robot within 3 s at their closing speed (`PEDESTRIAN_LANE_*`, `pedestrian_lane_penalty`, env `pedestrian_lane_times()`, step info `min_pedestrian_lane_time`), applied even while waiting, so the robot is paid to step aside early instead of only near contact; separate from the wall proximity penalty below); geodesic so the T-junction's inner corner isn't a local optimum. The geodesic charges extra within `SAFE_CLEARANCE` (0.6 m) of walls so its route rounds corners clear of the collision boundary, and a per-step proximity penalty (up to 0.5, `PROXIMITY_DISTANCE` 0.3 m between footprint and nearest obstacle; 2D env from map clearance, Gazebo from the full scan) teaches holding that route at speed. The 2D env also drops 3% of observed beams (no return, as on glass) during training. Step limit scales with start distance (2× full-speed time + 10 s). `DOOR_GOALS`: corridor-centerline points in front of each door in `hallway.sdf`, the fixed eval goal set (and seed for milestone 4).
- `cash_rl/occupancy_map.py`: loads the SLAM map (`$CASH_MAP_YAML`, else `maps/hallway.yaml` found by walking up from the source file — works with symlink install) and computes geodesic distance fields (Dijkstra on cells ≥0.25 m from obstacles, ~12 ms per goal on the hallway, ~100 ms on `cbu_floor2`; `limit=` stops early). **Maps:** `train`/`evaluate`/`dagger`/`view_env --map cbu_floor2` (name in `maps/` or a path; sets `$CASH_MAP_YAML` so subprocesses follow). `train`/`dagger` record `map_yaml` in `config.json`, and `evaluate`/`view_env` default to the model's map (warns on mismatch; runs without it are hallway). Hallway-only: `DOOR_GOALS` door evals (`env.door_goals` is empty elsewhere, so `evaluate` needs `--random N`) and `--junction-prob`. A `<map>_keepout.yaml` next to the map keeps spawns, goals and pedestrians out of its zones (the robot can still drive in). Pedestrians walk along y above y=1.5 on the hallway (unchanged, so hallway seeds reproduce); elsewhere along the longer open stretch through their cell, majority-voted over 1.5 m. `view_env` labels the layout's doors (`landmarks_for`). `demo` still assumes the hallway's doors.
- `cash_rl/raycast_env.py`: `HallwayRaycastEnv`, ROS-free 2D training env — unicycle model with the DiffDrive accel limits, raycasts the observed beams against the map (~2.3k steps/s single core). `reset(options={'spawn': (x, y, yaw), 'goal': (x, y)})`; omitted ones are sampled (random collision-free spawn, goal 1–15 m geodesic away). `info['is_success']` for SB3's EvalCallback; `render_mode='rgb_array'`. `n_pedestrians=N` (default 0, behavior unchanged) adds 0.25 m-radius discs that walk the corridor axis (x in the main corridor, y in the branch) at 0.5–0.9 m/s (0.8–1.4 before 2026-10-21), turn back at walls/obstacles, ignore each other; by default they also ignore the robot and walk straight into it if it stays in their path (getting out of the way is the robot's job). `pedestrians_yield=True` (`--yielding-pedestrians` in `train`/`evaluate`/`view_env`; how every pedestrian run before 2026-10-21 trained) restores the old behavior: with the robot ahead inside the 0.8 m comfort gap they slow to 30%, and if it is in their path they sidestep away at 0.5 m/s (stopping inside 0.3 m until the path is clear), then keep walking the same way; block beams (exact ray/disc intersection) and count as collisions; start ≥2 m from the robot, drawn after spawn/goal so seeded episodes are unchanged; positions in `env.pedestrians` / `info['pedestrians']`; step info adds `hit_pedestrian` and `min_pedestrian_gap`. 2D only — Gazebo has no pedestrians yet. `subgoal_lookahead=M` (`--subgoal-lookahead M` on `train`/`dagger`/`evaluate`/`view_env`) is the planner half of the hierarchy: the observation's goal becomes the point M m ahead on `route()` (the goal once closer); reward, success and step limit still use the real goal, so results stay comparable. `evaluate`/`view_env` default to the model's training setting (`config.json`), warning on a mismatch; `view_env` draws the subgoal as an orange ×. `subgoal_offset=W` (`--subgoal-offset W` on `train`/`dagger`/`evaluate`/`view_env`, needs a lookahead) puts the subgoal in a *lane* up to W m left/right of the corridor center (from the walls, so it doesn't drift with the robot; clipped to keep `SAFE_CLEARANCE`), redrawn every 2–6 s; `reset(options={'lane_offset': x})` / `evaluate --lane-offset x` pin it, and a decision layer can set `env.lane_offset` per step. `downhill`/`avoider` follow the lane 1 m ahead (`near_lane`), and an off-center lane picks the avoider's passing side (replacing keep-right), so DAgger teaches lane-following; the reward subtracts `spec.subgoal_lane_penalty` (0.5 per m beyond 0.1 m from the lane across the route at the robot, `robot_lane`, per step), so PPO is paid to follow subgoals. It is waived in turns (>30° between the robot and 1 m ahead), junctions/open areas and the last 3 m, where the lane ahead swings round; the progress reward telescopes, so following a lane away from the goal (e.g. right around a pedestrian when the goal is ahead-left) costs only its extra time (`test_following_a_lane_away_from_the_goal_is_not_penalized`). `evaluate` adds a `lane` column (mean |sideways error|). Checked against live Gazebo `/scan`: median beam error ~6 cm, which is the SLAM map's ±1 cell wall placement, not the raycaster.
- `cash_rl/decision.py`: rule-based decision layer (upper half of the hierarchy; the planner places the subgoal along the route, this picks its lane). `PedestrianLaneDecider`: no pedestrian in the way → center lane; a pedestrian ahead within 6 m, inside 1.5 m of the robot's line and closing (oncoming or overtaken) → lane 0.8 m beside the pedestrian's line on the side with more room where they'll meet (±1 m; keep right on ties), measured from the followed lane's center, held until the pedestrian is 0.8 m behind. `DecisionLayer` wrapper sets `env.lane_offset` each step and rebuilds the obs; `evaluate`/`view_env --decision-layer`. Privileged (true pedestrian positions); on the robot this needs LiDAR tracking. Limits: no "wait" (dead-center pedestrian in the 2.4 m hallway, fountain stretch), no lanes in the last 3 m, ignores pedestrians from behind. TEGR encounter test, 200 held-out goals: `downhill` (pure lane follower) 53% center lane → 91% with it; avoider 89% alone → 94% with it.
- `cash_rl/hallway_env.py`: `HallwayEnv`, the same task in Gazebo over rclpy (`/scan`, `/cmd_vel`, ground-truth `/model/cash_bot/pose` — odom drifts ~15 m per mapping pass, so it isn't used). reset() calls ControlWorld (model_only reset) then SetEntityPose to teleport to `options['spawn']` (default `spec.SPAWN_POSE`); goal defaults to a random `DOOR_GOALS` entry. Steps on wall-clock time (0.1 s), not sim time.
- `cash_rl/view_env.py` (console script `view_env`): plays `HallwayRaycastEnv` episodes in a matplotlib window (or `--save x.gif`) — map to scale, footprint, beams, goal, trail, step/return/outcome. `--policy downhill|random`, `--goal random|all|door_XXX`, `--pedestrians N` (purple discs). GUI: ask me to run it, don't launch it yourself.
- `cash_rl/demo.py` (console script `demo`): interactive 2D demo — left-click places the robot (drag to aim; a plain click faces +x), right-click sets the destination (or 1–7 for a door), Esc clears; chains legs from where the robot stopped. Defaults to the newest `runs/*/best_model.zip`. Drawing shared with `view_env` via `view_env.Scene`. GUI: ask me to run it.
- `cash_rl/scripted.py`: `downhill`, a hand-written reference controller that cheats (reads the map's geodesic field); used by tests and `view_env` as a baseline.
- `cash_rl/train.py` (console script `train`): SB3 training on `HallwayRaycastEnv` (`--algo ppo|sac|td3`, default PPO 3M steps (~38 min on this laptop), 12 `SubprocVecEnv`s, `--goal-distance-range MIN MAX` for training goals, `--pedestrians N` for moving pedestrians in training *and* eval (runs are comparable only at equal counts), `--junction-prob P` for the share of episodes with spawn and goal on opposite sides of the junction (drawn only when > 0, so seeded episodes are unchanged at 0); PPO hyperparameters are `algo_kwargs` in `train.py`; eval always uses the default range so runs stay comparable). Writes `runs/<name>/` (gitignored): `config.json`, TensorBoard logs, `eval.csv`, `checkpoints/`, `best_model.zip`, `final_model.zip`. `GoalEvalCallback` evaluates deterministically every 100k steps on all `DOOR_GOALS` from spawn + 20 fixed-seed random pairs, logging success/collision/timeout rate and return (`eval/*`) — use those curves in the report, not training reward. `view_env --policy runs/<name>/best_model.zip` watches a trained model.
- `cash_rl/evaluate.py` (console script `evaluate`): runs a trained model on every `DOOR_GOALS` entry from spawn and prints per-door outcome/steps/return; `--env 2d` (default) or `--env gazebo` (needs `train_env.launch.py`); `--pedestrians N` adds moving pedestrians (2D only). Takes several model paths to compare them side by side; `--random N` adds N held-out random spawn/goal pairs (2D only). Run Gazebo evals with training stopped — `HallwayEnv` steps on wall-clock time, and training load drops Gazebo's real-time factor to 0.6–2×.
- `cash_rl/safety.py`: LiDAR safety layer for deployment and eval. `limit_command(linear, angular, ranges, angles)` simulates the command over its stopping time and falls back to gentler commands if the footprint would come within `SAFETY_MARGIN` (0.10 m) of a scan point; moving away is always allowed. Pure numpy, meant to run on the Jetson. `SafetyWrapper` applies it to an env (both envs have `safety_scan()`); `evaluate --safety` uses it (cut collisions 4.2% → 0.7% over 3 seeds).
- `docs/MODELS.md`: comparison of every trained model (settings, PPO hyperparameters, learning curves `docs/learning_curves.png`, 200-goal held-out results, seed variation, safety layer). Update it whenever a model is added; the README's results table summarizes it.
- `cash_rl/random_agent.py` (console script `random_agent`): drives `HallwayEnv` with random actions for a few episodes — smoke test for reset/step/service-bridge before wiring up real training.
- `launch/train_env.launch.py`: includes `cash_sim`'s `sim.launch.py` headless plus a `ros_gz_bridge` for the `/world/hallway/control` and `/world/hallway/set_pose` services and the `/model/cash_bot/pose` ground-truth topic (none are in `cash_sim/config/bridge.yaml`).
- Runtime deps `gymnasium`/`numpy` are pip, not rosdep-resolvable here — installed via `pip install --user --break-system-packages gymnasium` (numpy stayed at the system 1.26.4).
- Episode reset calls `ControlWorld` (world reset, clears sim time/physics state) *and* `SetEntityPose` targeting the `cash_bot` entity by name — `ControlWorld`'s `model_only` reset alone does not restore pose for entities spawned dynamically after world load (confirmed by smoke test: episodes collapsed to 1-4 steps because the robot never left the wall it crashed into), so the explicit teleport is required, not just a nice-to-have.

## Conventions
- Installed via pip (user site): CPU-only `torch` (from the PyTorch CPU index), `stable-baselines3`, `tensorboard`. This also put `setuptools` 78 and `protobuf` 7 in the user site, shadowing the apt versions; colcon builds and ROS imports were checked and still work.
- Run one training at a time, and set `OMP_NUM_THREADS=1` when running evaluations in parallel: each PyTorch process grabs all 22 threads, and two concurrent trainings stalled for 15 min.
- Compare setups by the mean over 3 seeds on `evaluate --random 200`; single runs vary ±3% in success. The 27-episode periodic eval can't rank models, and its `best_model.zip` is often worse than `final_model.zip`.
- Install Python packages with `pip install --user --break-system-packages`; when installing `torch` or `stable-baselines3`, always pin `"numpy<2"` alongside them so they don't upgrade the system numpy (1.26.4) that ROS 2 Jazzy's Python packages expect
- Jazzy + Gazebo Harmonic only: `ros_gz` and `gz-sim-*` system plugins, never Gazebo Classic / `gazebo_ros`
- Absolute topic names; `use_sim_time: true` on all sim nodes
- Never commit `build/`, `install/`, `log/`, rosbags, or trained model weights
- Small commits with clear messages
- Add a dated section to `WORKLOG.md` (newest first) at the end of each work session
